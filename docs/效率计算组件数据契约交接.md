# 效率计算组件：数据源与输入契约交接

本文用于将当前基建效率计算逻辑拆分为可供其他项目调用的独立组件。本文描述的是目标组件的输入边界、数据源和数据格式，不包含 Vue 页面、页面展示格式或图片资源。

## 1. 已确认的总体边界

- 计算核心应保持纯函数：输入排班、干员技能目录、共享术语目录和规则集，输出效率结果。
- 独立组件不读取当前项目的 `public/assets`、Vue composable、浏览器 `localStorage` 或页面状态。
- 当前项目负责提供数据加载适配器；其他项目也可以使用自己的数据加载方式。
- 当前项目的 Torappu 原始 JSON 不直接作为计算核心的公共输入，先转换为稳定的归一化格式。
- 干员技能 JSON 可以合并干员基础信息，避免计算组件同时依赖独立的干员基础信息表。
- 组件不需要头像、技能图标、物品图标、立绘、富文本样式和页面文案。
- `processing` 和 `training` 可以保留在排班输入中，用于技能条件和设施范围判断，但当前版本不直接生成它们的效率产出。

## 2. 数据依赖总览

| 数据类别         | 是否必需     | 作用                                   | 推荐来源                                   |
| ---------------- | ------------ | -------------------------------------- | ------------------------------------------ |
| 排班文档         | 是           | 当前布局、队列、设施、干员、产物和设置 | 调用方业务数据                             |
| 干员技能文档     | 是           | 技能链、解锁条件和结构化效果           | 版本化生成的技能 JSON                      |
| 干员基础信息     | 是           | ID、名称、稀有度和术语归属             | 合并进每名干员的 JSON                      |
| 术语信息         | 是           | 阵营、技能术语和术语成员匹配           | `packages/riic-efficiency/data/terms.json` |
| 设施与生产规则   | 是           | 基础效率、等级、容量、配方、订单和产出 | 版本化规则集                               |
| 干员练度档案     | 否           | 拥有状态、实际精英化和等级             | 调用方用户数据                             |
| 排班局部状态     | 否           | 当前队列中的心情、强制练度等           | 排班文档中的 `operatorStates`              |
| 无人机策略       | 否           | 计算额外无人机加速场景                 | 调用方设置或单独 API                       |
| Torappu 原始数据 | 仅适配器需要 | 生成上述归一化数据                     | 当前项目数据目录                           |

## 3. 推荐公共调用接口

目标形式为：

```ts
const result = calculateEfficiency(schedule, {
  catalog,
  ruleset,
});
```

下面的数据边界保持独立：

- `schedule`：一次或多次排班队列和当前用户设置；
- `catalog`：干员 JSON、技能和共享术语目录构建出的运行时目录；
- `ruleset`：游戏版本相关的设施、生产和常量规则；
- `schedule.settings`：用户练度档案、技能解锁开关、宿舍默认练度开关和其他排班状态。

## 4. 排班输入格式

### 4.1 设施布局

设施必须以有序列表提供。只提供设施类型数量不够，因为同类型设施需要区分物理实例、等级和顺序。

```json
{
  "layout": [
    { "type": "control", "level": 5 },
    { "type": "trading", "level": 3 },
    { "type": "trading", "level": 3 },
    { "type": "manufacture", "level": 3 },
    { "type": "power", "level": 3 },
    { "type": "power", "level": 3 },
    { "type": "power", "level": 3 },
    { "type": "meeting", "level": 3 },
    { "type": "hire", "level": 3 },
    { "type": "dormitory", "level": 5 }
  ]
}
```

允许的设施类型：

```ts
type RoomKey =
  | "control"
  | "trading"
  | "manufacture"
  | "power"
  | "meeting"
  | "hire"
  | "processing"
  | "training"
  | "dormitory";
```

当前项目可以根据同类型出现顺序生成 ID：

```text
第一个贸易站 -> trading-1
第二个贸易站 -> trading-2
第一个制造站 -> manufacture-1
```

独立组件也可以直接接受显式 ID：

```json
{
  "id": "trading-1",
  "type": "trading",
  "level": 3
}
```

如果使用显式 ID，ID 必须在整个排班文档内稳定且唯一。物理设施 ID 用于：

- 同类型设施区分；
- `same` 和目标设施判断；
- 心情和槽位连续性；
- 设施级 `firstItemProgress`；
- 结果中的设施归属。

### 4.2 队列和设施排班

```json
{
  "plans": [
    {
      "name": "第一队列",
      "duration": 720,
      "rooms": {
        "control": [
          {
            "operators": ["夕", "稀音"]
          }
        ],
        "trading": [
          {
            "product": "龙门币",
            "operators": ["德克萨斯", "能天使", "空"]
          },
          {
            "product": "合成玉",
            "sourceMaterial": "固源岩",
            "operators": ["孑"]
          }
        ],
        "manufacture": [
          {
            "product": "赤金",
            "operators": ["煌", "精二干员"]
          }
        ],
        "power": [{ "operators": [] }, { "operators": [] }, { "operators": [] }]
      }
    }
  ]
}
```

`rooms[type]` 中同类型设施的数组顺序必须与 `layout` 中同类型设施的顺序对应：

- `rooms.trading[0]` 对应第一个贸易站；
- `rooms.trading[1]` 对应第二个贸易站；
- `rooms.power[0]` 对应第一个发电站。

排班字段：

```ts
interface RoomAssignment {
  operators?: string[];
  skip?: boolean;
  product?: string;
  sourceMaterial?: string;
  operatorStates?: Record<string, OperatorState>;
}
```

字段语义：

- `operators`：槽位顺序排列的干员名称；
- `skip`：该设施在当前队列中跳过工作；
- `product`：贸易站或制造站的目标产物；
- `sourceMaterial`：源石碎片制造时使用的材料；
- `operatorStates`：当前队列、当前物理设施中的局部干员状态。

### 4.3 干员局部状态

当前有效字段：

```ts
interface OperatorState {
  mood?: number;
  elite?: number;
  level?: number;
}
```

示例：

```json
{
  "operators": ["能天使"],
  "operatorStates": {
    "能天使": {
      "mood": 12,
      "elite": 2,
      "level": 60
    }
  }
}
```

这些状态只作用于当前排班中的当前干员，不写入干员技能文档。未来可以在同一个对象中扩展技能开关或排班专用状态，但新增字段必须有明确的计算语义。

### 4.4 队列时长

`duration` 使用分钟：

```json
{
  "duration": 720
}
```

表示 12 小时。未提供时当前规则使用 720 分钟作为默认值。多个队列的每日产出按各自的工作时长加权，再除以总循环小时数换算到每日。

### 4.5 排班设置

```ts
interface ScheduleSettings {
  clueExchanging?: boolean;
  dormFullTreat?: boolean;
  fiammettaMode?: "queue" | "direct";
  fiammettaDirectCount?: number;
  preferMaxJieEfficiency?: boolean;
  lmdDroneStrategy?: string;
  tradeOrderCount?: Record<string, number>;
  overflowMode?: "continue" | "zero";
  firstItemProgress?: number | Record<string, number>;
  progressionProfile?: OperatorProgressionProfile;
  treatSkillsAsUnlocked?: boolean;
  dormitoryDefaultIncludesMoodRecovery?: boolean;
}
```

默认值：

```json
{
  "clueExchanging": true,
  "dormFullTreat": true,
  "fiammettaMode": "direct",
  "fiammettaDirectCount": 3,
  "preferMaxJieEfficiency": true,
  "overflowMode": "continue",
  "firstItemProgress": 0
}
```

#### 第一件产品进度

`firstItemProgress` 表示当前物理设施第一件产品已经完成的比例，范围为 `0..1`：

```json
{
  "firstItemProgress": 0.5
}
```

也可以按物理设施或设施类型提供：

```json
{
  "firstItemProgress": {
    "trading-1": 0.5,
    "manufacture": 0.25
  }
}
```

它用于首件产品、容量爆仓和孑精 0 的效率积分，不表示贸易站已有多少订单。

#### 贸易站已有订单数量

独立组件使用直接订单数量，不使用百分比：

```json
{
  "tradeOrderCount": {
    "trading-1": 5
  }
}
```

它表示当前贸易站已经存在的订单数，必须是整数，并限制在当前设施订单上限内。它只在技能规则读取 `orderCount` 时参与计算，当前实际消费者是孑精一“市井之道”。

当前项目没有用户可手动调整旧 `orderProgress` 的入口，因此独立组件不设计旧字段兼容转换，也不需要从 `firstItemProgress` 推导订单数量。迁移当前项目时直接使用新的 `tradeOrderCount`；没有该状态时按 `0` 个订单处理。

### 4.6 菲亚梅塔配置

```ts
interface FiammettaScheduleState {
  queue?: RoomAssignment[];
  direct?: RoomAssignment;
}
```

菲亚梅塔是计算用的假设施配置，不写入真实设施布局。具体使用哪个配置由 `fiammettaMode` 决定。

## 5. 干员技能目录格式

推荐把干员基础信息和技能链合并为一个版本化 JSON 文档。每名干员都必须生成一个 JSON 文件，或在等价的聚合目录中保留一条记录。

生成范围不能只限于当前效率计算目标设施中的干员。以下干员也必须生成文档：

- 只有加工站技能的干员；
- 只有训练室技能的干员；
- 只有宿舍、控制中枢或其他暂不直接产出设施技能的干员；
- 当前没有可解析效率技能，但属于某个阵营或术语的干员。

这些干员即使 `chains` 为空，仍然需要保留 `id`、`name` 和 `rarity`。术语成员统一从共享术语目录读取，不能依赖干员 JSON 中的字段。

### 5.1 干员技能文档

```json
{
  "schemaVersion": 2,
  "id": "char_002_amiya",
  "name": "阿米娅",
  "rarity": 5,
  "chains": [
    {
      "slot": 1,
      "room": "trading",
      "stages": [
        {
          "unlock": {
            "type": "elite",
            "value": 1
          },
          "name": "示例技能",
          "effects": []
        }
      ]
    }
  ]
}
```

字段：

```ts
interface OperatorSkillDocument {
  schemaVersion?: number;
  id: string;
  name: string;
  rarity: number;
  chains: EfficiencySkillChain[];
}
```

### 5.2 星级与最大练度

当前规则可以从稀有度推导：

| 稀有度 | 最大精英化 | 精 0 | 精 1 | 精 2 |
| -----: | ---------: | ---: | ---: | ---: |
|      1 |          0 |   30 |    - |    - |
|      2 |          0 |   30 |    - |    - |
|      3 |          1 |   40 |   55 |    - |
|      4 |          2 |   45 |   60 |   70 |
|      5 |          2 |   50 |   70 |   80 |
|      6 |          2 |   50 |   80 |   90 |

干员 JSON 不保存 `maxEliteLevel` 或 `maxLevelByElite`。计算组件根据 `rarity` 和规则集中的星级练度表推导最大精英化阶段和最大等级。技能阶段中的 `unlock` 仍然单独表示技能何时解锁，不能用星级练度上限代替。

### 5.3 技能链和阶段

```ts
interface EfficiencySkillChain {
  slot: number;
  room: RoomKey | string;
  stages: EfficiencySkillStage[];
}

interface EfficiencySkillStage {
  unlock: {
    type: "elite" | "level" | string;
    value: number;
  };
  name: string;
  effects: EfficiencyEffect[];
}
```

`room` 表示技能来源设施。当前计算目标主要是：

```text
control / trading / manufacture / power / meeting / hire / dormitory
```

加工站和训练室可以作为技能条件或设施范围存在，但当前版本不直接生成它们的效率产出。只有这些设施技能的干员仍然必须生成 JSON；其 `chains` 可以包含对应设施技能，也可以在技能无法参与当前计算时为空，但基础信息不能省略。

```ts
  value?: number;

  curve?: EfficiencyCurve;

  scope?: "self" | "room" | "op" | string;
  op?: string;
  scopeGroup?: string;
  subjects?: "single" | "spread" | string;
  other?: boolean;
  stack?: "max" | string;
  maxGroup?: string;
  baseValue?: number;
  recipe?: string;
  term?: string;
  from?: string;
  to?: string;
  rate?: number;
  order?: EfficiencyOrderRule;

  except?: string[];

  tagTo?: string;
```

未知字段应在读取和重新序列化时保留，以便以后增加技能语义时不破坏旧数据。

## 6. 共享术语文件

术语信息独立存储在 `packages/riic-efficiency/data/terms.json`。该文件由生成器直接读取 `gamedata_const.json.termDescriptionDict` 生成，不读取干员技能 JSON，也不由干员文件去重得到。

```json
{
  "schemaVersion": 2,
  "terms": {
    "cc.g.example": {
      "name": "示例阵营",
      "members": ["干员A", "干员B", "干员C"],
      "definition": "术语描述"
    }
  }
}
```

```ts
interface EfficiencyTerm {
  name?: string;
  members?: string[];
  definition?: string;
}

type EfficiencyTerms = Record<string, EfficiencyTerm>;
```

`members` 由生成器直接从源术语描述中的干员、技能和设施列表生成。动态术语由生成器结合 `character_table.json` 等源数据展开。没有成员列表的术语仍然需要保留，因为技能效果可能直接引用它们。

组件公共 API 接收共享术语目录：

```ts
const catalog = createEfficiencyCatalog(operatorFiles, termsFile.terms);
```

## 7. 两类特殊排班占位符

排班中的 `operators` 不一定全部是真实干员。组件必须识别以下两类特殊值。

### 7.1 百分比占位符

例如：

```json
{
  "operators": ["20%"]
}
```

这类值没有干员技能文档，名称本身表示百分比效率。组件根据设施类型将其映射为对应效率属性。

### 7.2 术语占位符

术语 key 或术语显示名称也可能出现在排班中：

```json
{
  "operators": ["示例阵营"]
}
```

这类值通过 `terms` 目录解析，不应当作为缺失干员报告错误。它们用于群组统计、术语条件和特殊排班表达。

## 8. 可选的干员练度档案

如果调用方需要根据用户实际拥有状态和练度决定技能是否生效，可以传入：

```json
{
  "id": "profile-1",
  "name": "默认档案",
  "entries": {
    "char_002_amiya": {
      "id": "char_002_amiya",
      "name": "阿米娅",
      "elite": 2,
      "level": 80,
      "owned": true,
      "rarity": 5
    }
  },
  "importedEntries": {},
  "createdAt": "2026-09-20T00:00:00.000Z",
  "updatedAt": "2026-09-20T00:00:00.000Z"
}
```

```ts
interface OperatorProgressionEntry {
  id: string;
  name: string;
  elite: 0 | 1 | 2;
  level: number;
  owned: boolean;
  rarity: number;
}

interface OperatorProgressionProfile {
  id: string;
  name: string;
  entries: Record<string, OperatorProgressionEntry>;
  importedEntries: Record<string, OperatorProgressionEntry>;
  createdAt: string;
  updatedAt: string;
}
```

这些字段属于排班设置，不作为 `calculateEfficiency` 的额外参数。调用方不提供练度档案时，组件仍根据排班局部状态和默认技能解锁规则计算；缺失档案不能导致整个效率计算失败。

### 9.4 贸易订单

```ts

  probability: number;
  ignoreEfficiency?: boolean;
```

当前订单规则按贸易站等级提供。例如三级贸易站：

还需要单独表达合成玉订单和裁缝订单概率，不要把它们强行转成普通贸易效率百分比。

### 9.5 资源键别名

计算层建议统一使用中文实际资源名，同时保留输入别名归一化：

```json
{
  "LMD": "龙门币",
  "Orundum": "合成玉",
  "Pure Gold": "赤金",
  "Battle Record": "中级作战记录",
  "Originium Shard": "源石碎片",
  "作战记录": "中级作战记录",
  "贵金属": "赤金"
}
```

制造类型和实际产物要分开：

- `recipe: "贵金属"` 表示制造类型；
- `product: "赤金"` 表示实际产物。

## 10. 其他固定规则

以下规则也属于效率计算语义，应由规则集或明确的版本化计算模块提供：

- 稀有度基础效率：六星 `5`、五星 `4`、四星 `2`，其他稀有度 `0`；
- 精英化基础效率：精二 `16`、精一 `8`、精零 `0`；
- 会客室基础产出：1 条线索/20 小时；
- 每条线索折算 40 信用；
- 线索上限为 11；
- 办公室基础产出为 1 次公开招募/12 小时；
- 公开招募次数上限为 3；
- 发电站基础产出为 10 无人机/小时，并按发电站组处理；
- 菲亚梅塔使用计算用假设施，不修改真实布局；
- `overflowMode: "zero"` 在容量耗尽后截断有效产出；
- `overflowMode: "continue"` 保留计划产出；
- 贸易站和制造站材料流使用有符号值，产出为正、消耗为负；
- `cc.t.flow_gold` 等基地点数术语和特殊点数链需要保留规则标识。

## 11. 当前项目的原始数据适配器

当前项目拥有以下 Torappu 原始数据：

```text
public/assets/gamedata/latest/excel/character_table.json
public/assets/gamedata/latest/excel/building_data.json
public/assets/gamedata/latest/excel/gamedata_const.json
public/assets/gamedata/latest/excel/item_table.json
public/assets/gamedata/latest/torappu-meta.json
packages/riic-efficiency/data/operators/{operatorId}.json
```

适配职责：

### `character_table.json`

提供或辅助提供：

- 干员 ID；
- 干员名称；
- 稀有度；
- 原始角色和技能元数据。

### `building_data.json`

提供或辅助提供：

- 基建技能描述；
- 技能链和设施归属的原始数据；
- 生成结构化技能效果所需的信息。

### `gamedata_const.json`

提供：

- 术语 key；
- 术语名称；
- 术语描述；
- 富文本术语中的成员信息。

这些原始数据只参与宿主展示和技能 JSON 生成；效率运行时使用组件数据目录中的共享 `terms.json`。

宿主适配器应直接从 `packages/riic-efficiency/data/operators/` 读取结构化文件，而不是让计算器依赖 Torappu 原始对象结构。

### `operators/{operatorId}.json`

这是当前项目已经生成的结构化技能数据。独立组件可以直接使用它，并在生成阶段为每名干员保留以下基础信息：

- `id`；
- `name`；
- `rarity`。

生成器必须遍历完整的干员基础数据，而不是只遍历成功生成了目标设施技能的干员。没有独立技能 JSON 的干员也必须输出最小文档，例如：

```json
{
  "schemaVersion": 2,
  "id": "char_example",
  "name": "仅加工站技能干员",
  "rarity": 4,
  "chains": []
}
```

### `terms.json`

该文件与 `operators/`、`ruleset.json` 一起发布，由 `manifest.json` 的 `terms` 字段指向。宿主加载后将 `terms` 对象传给 `createEfficiencyCatalog`。

### `torappu-meta.json`

用于记录数据版本和生成来源，推荐在目录元数据中保留：

```json
{
  "gameVersion": "...",
  "source": "torappu",
  "syncedAt": "...",
  "schemaVersion": 1
}
```

### `item_table.json`

当前效率核心不是必需的。它主要服务于物品名称、图标和页面显示。如果独立组件只输出数值和资源键，可以不传入。

## 12. 不属于效率计算核心的数据

以下数据不应成为独立组件的必需依赖：

- 干员头像和立绘；
- 技能图标；
- 物品图标；
- 富文本样式表；
- Ant Design Vue 组件；
- Vue Router；
- 浏览器 `fetch`；
- `localStorage`；
- 页面设置 composable；
- 图片导出和页面格式化函数；
- 旧项目 CSV；
- Maa 导入导出格式。

Maa、TXT 和其他项目的输入格式应在效率组件外部先转换为统一的 `ScheduleDocument`。

## 13. 目录版本和校验建议

建议每个可调用的数据目录包含元数据：

```json
{
  "schemaVersion": 2,
  "rulesetVersion": "arknights-riic-2026-09",
  "gameDataVersion": "...",
  "generatedAt": "2026-09-20T00:00:00.000Z",
  "operators": "operators",
  "terms": "terms.json",
  "ruleset": "ruleset.json"
}
```

加载时至少校验：

- schema 版本是否支持；
- 干员 ID 是否唯一；
- 干员名称是否唯一；
- `rarity` 是否为 1 到 6；
- 最大精英化等级和最大等级是否符合星级规则；
- 技能链设施类型是否有效；
- `unlock` 数值是否为整数；
- 每个技能效果引用的术语 key 是否能在共享 `terms.json` 中解析；
- 贸易订单概率总和是否符合规则集约定；
- 设施 ID 是否唯一；
- `tradeOrderCount` 是否为整数且不超过当前订单上限；
- `firstItemProgress` 是否在 `0..1` 范围内。

技能文件缺失时，建议保留该干员的基础效率计算，并在结果中返回结构化错误或警告，而不是阻断其他设施计算。

## 15. 当前交接结论

主会话实现时应优先确定以下边界：

1. 计算核心接收归一化目录和独立的共享术语目录，不直接解析 Torappu 原始 JSON。
2. 每名干员都生成一个技能 JSON；基础信息至少包括 ID、名称和稀有度，最大精英化等级与最大等级由稀有度规则推导，不写入干员 JSON。
3. 只有加工站、训练室或其他暂不参与效率产出的技能的干员，也必须生成包含基础信息的 JSON。
4. 设施使用有序列表或带稳定 ID 的物理设施列表，不能只传设施数量。
5. `firstItemProgress` 保留为第一件产品进度，范围为 `0..1`。
6. 订单状态使用直接的 `tradeOrderCount`，不使用百分比。
7. 当前项目没有用户可编辑的旧 `orderProgress`，独立组件不设计旧字段兼容转换。
8. 百分比占位符和术语占位符属于合法排班成员，不应当作为缺失干员处理。
9. 生产规则、订单规则、容量规则和常量需要版本化，避免其他项目复制当前页面实现。
10. UI、资源图片、Maa/TXT 适配器和浏览器加载逻辑留在独立组件之外。
