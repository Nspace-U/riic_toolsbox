## 3. 队列和时间

- 一个排班表可以有一个或多个队列。
- 旧项目默认 3 个队列，每个队列间隔 12 小时。
- 当前项目 `Plan.duration` 使用分钟保存，默认值为 720 分钟；计算时应转换为小时：`durationHours = duration / 60`。
- 同一排班表的队列按顺序循环：队列 1 -> ... -> 队列 N -> 队列 1。
- 每日平均产出：

  `每日产出 = 一轮各队列产出之和 × 24 ÷ 一轮总时长`

- 旧项目的容量计算从每个队列的空库存开始；队列结束视为库存清空。是否保留此口径，需要当前项目确认。

来源：旧项目 `基建模拟器文档.md` §队列（第 100-110 行）和 §功能二（第 120-134 行）。当前项目排班结构见 `src/types/schedule.ts`。

## 4. 固定产出

基础耗时单位为小时，表示效率 100% 时完成一次产出所需时间。

| 设施                     | 产品                 | 数量 | 基础耗时 | 基础速率 |
| ------------------------ | -------------------- | ---: | -------: | -------: |
| 发电站（所有发电站合并） | 无人机               |    1 |      0.1 |     10/h |
| 会客室（每座独立）       | 线索                 |    1 |       20 |    1/20h |
| 办公室（每座独立）       | 公开招募标签刷新次数 |    1 |       12 |    1/12h |

发电站数量不增加无人机基础产出速率；多座发电站只增加电力和可进驻位置。最终速率通常为 `基础速率 × 最终效率 / 100`。

会客室每获得 1 条线索可兑换 40 信用点，因此基础信用点折算速率为 `40/20=2/h`；线索产出速率和线索容量速率保持独立，线索上限为 11 条。

佩佩的特别独占订单是例外：该订单产出率固定为 `1000 / 4.5`，不乘贸易站最终效率。

来源：旧项目 `基建模拟器文档.md` §设施产出（第 122-134 行）和 `贸易站龙门商法策略.md` §模拟器结算规则第 5 条。

## 6. 贸易站基础规则

### 6.1 龙门商法普通订单

| 贸易站等级 | 订单         | 龙门币 | 赤金消耗 | 基础耗时 |
| ---------: | ------------ | -----: | -------: | -------: |
|          1 | 2 贵金属订单 |   1000 |        2 |     2.4h |
|          2 | 2 贵金属订单 |   1000 |        2 |     2.4h |
|          2 | 3 贵金属订单 |   1500 |        3 |     3.5h |
|          3 | 2 贵金属订单 |   1000 |        2 |     2.4h |
|          3 | 3 贵金属订单 |   1500 |        3 |     3.5h |
|          3 | 4 贵金属订单 |   2000 |        4 |     4.6h |

订单概率：

| 订单         | 1 级 | 2 级 | 3 级 |
| ------------ | ---: | ---: | ---: |
| 2 贵金属订单 | 100% |  60% |  30% |
| 3 贵金属订单 |   0% |  40% |  50% |
| 4 贵金属订单 |   0% |   0% |  20% |

基础产出率采用期望收益除以期望耗时，而不是先分别计算每种订单的每小时收益再相加：

`基础产出率 = Σ(概率 × 龙门币数量) ÷ Σ(概率 × 订单耗时)`

最终产出率通常为 `基础产出率 × 贸易站最终效率 / 100`。

### 6.2 开采协力

三级贸易站可选择开采协力，固定订单为：20 合成玉，消耗 2 个源石碎片，基础耗时 2 小时。该策略不受裁缝、但书、龙舌兰等龙门商法特殊订单技能影响。

### 6.3 裁缝类订单概率

裁缝类仅在三级贸易站生效。按同一贸易站中生效的技能数量查表：

| 生效组合        | 2 贵金属 | 3 贵金属 | 4 贵金属 |
| --------------- | -------: | -------: | -------: |
| 1 个 α          |      15% |      30% |      55% |
| 2 个 α          |      13% |      22% |      65% |
| 1 个 α + 1 个 β |       5% |      10% |      85% |

未登记的组合（例如单独 β、β+β、3 个 α）整体不生效，回退三级贸易站默认概率 30%/50%/20%。

### 6.4 特殊订单优先级和金额

优先级：佩佩 > 可露希尔 > U-Official > 但书 = 龙舌兰。

| 干员规则   | 订单结果                                                                                 |
| ---------- | ---------------------------------------------------------------------------------------- |
| 佩佩       | 固定 1000 龙门币、无赤金、4.5h；不受效率影响                                             |
| 可露希尔   | 固定 1200 龙门币、消耗 2 赤金、2.4h；按效率影响产出                                      |
| U-Official | 保留无 U 时的概率和耗时（裁缝仍生效），金额固定为 1000 龙门币/2 赤金；但书和龙舌兰不生效 |
| 但书 α/β   | 2/3 贵金属订单分别额外消耗 1/2 赤金，额外获得 500/1000 龙门币；耗时不变                  |
| 龙舌兰 α/β | 4 贵金属订单额外获得 250/500 龙门币；赤金消耗和耗时不变                                  |

佩佩或可露希尔在场时，裁缝、但书、龙舌兰全部不生效。没有前三者时，但书和龙舌兰可以同时作用于各自订单。

来源：旧项目 `贸易站龙门商法策略.md` §特殊订单和 §模拟器结算规则（第 57-123 行）；旧项目 `基建模拟器文档.md` 第 152-181 行。

### 6.5 贸易站订单上限

贸易站基础订单上限按等级为 6/8/10。每完成一个订单消耗一个订单容量，最终上限不能低于 1。

当前技能 JSON 还会提供 `orderLimit`、`tradeOrder`、`orderLimitNet` 等效果。订单上限属于属性层，不与 `tradeSpd` 相加。孑、灵知、锏、琳琅之间存在顺序依赖，建议单独实现一个订单属性结算步骤：

1. 汇总干员提供的订单上限和灵知的谢拉格计数。
2. 按订单上限净值计算锏的冠军风采加成。
3. 汇总除孑/招商引资外的贸易效率。
4. 计算孑精 1 的订单上限扣除。
5. 得到额外订单上限，再计算琳琅招商引资和孑技能。

这部分旧项目已有明确的具体公式，但涉及当前技能 JSON 的特殊效果联合求值，建议实现前单独核对旧项目 `干员技能JSON规范.md` §计算规则第 16 条。

## 7. 效率组成

最终效率统一表示为百分比数值：

`最终效率 = 设施基础效率 + 干员效率 + 干员技能效率`

### 7.1 设施基础效率

| 设施             |                      基础效率 |
| ---------------- | ----------------------------: |
| 贸易站           |                          100% |
| 制造站           |                          100% |
| 发电站（合并组） |                          100% |
| 办公室           |                          100% |
| 会客室           | 1/2/3 级分别为 107%/109%/111% |

会客室另加宿舍总氛围：

| 宿舍总氛围  | 会客室加成 |
| ----------- | ---------: |
| 0-1999      |         0% |
| 2000-2999   |         5% |
| 3000-3999   |        10% |
| 4000 及以上 |        15% |

### 7.2 干员基础效率

| 设施           | 干员基础效率                            |
| -------------- | --------------------------------------- |
| 贸易站、制造站 | 每名心情大于 0 的干员 +1%               |
| 发电站、办公室 | 每名心情大于 0 的干员 +5%               |
| 会客室         | 每名心情大于 0 的干员 +5%，另加练度效率 |

会客室练度效率：

- 稀有度：4 星 +2%，5 星 +4%，6 星 +5%；1-3 星为 0%。
- 精英：精 1 +8%，精 2 +16%；1/2 星无精英加成，3 星最多精 1。
- 练度加成不受心情影响；会客室最终还要叠加心情 +5%。

心情 0 的干员不提供心情效率。计算全程保持原始浮点数，显示时再格式化，不在核心层四舍五入。

来源：旧项目 `基建模拟器文档.md` §设施基础效率（第 183-219 行）和 `心情机制.md` §6.1（第 154-168 行）。

## 8. 心情规则

### 8.1 状态和工作判定

- 心情范围为 0-24，未设置时默认 24，允许小数。
- 心情 `<= 0` 视为未工作：不消耗心情、不提供心情效率、不激活该干员技能链。
- 工作设施是控制中枢、贸易站、制造站、发电站、会客室、办公室；加工站、训练室和宿舍不消耗心情。
- 技能条件中的“是否算作进驻”不一律等同于心情 0。是否过滤心情由技能 JSON 的 `moodCheck` 决定；未标记时心情 0 仍可能被计入条件或 `per` 计数。

### 8.2 每小时消耗

对一个工作干员：

`消耗率 = 1 - 0.05 × 当前队列控制中枢工作人数 - 贸易/制造人数减免 + 技能心情修正`

- 控制中枢每名心情大于 0 的干员，使所有工作干员消耗率减少 0.05/h。
- 贸易站或制造站内有 2 名心情大于 0 的干员时，该设施内每名干员减少 0.05/h；有 3 名时减少 0.10/h。
- `moodCost` 正数增加消耗，负数减少消耗；`moodRecover` 等价为减少消耗。
- `zeroOpMood` 清除受影响干员通过个人作用范围获得的自身技能心情修正，不区分正负，不清除基础 1/h；不会清除房间共享效果，即使提供者本人也在目标房间。槐琥只清除同制造站干员各自的个人技能心情效果，不清除黍等干员施加给全站的共享效果。
- 令的 `zeroOpMood` 限定岁阵营和当前控制中枢，会清除其他干员施加给该中枢岁干员的 `moodCost` 与 `moodRecover`；其他中枢干员仍可获得夕提供的 `+0.05/h`。夕自身不获得自己的 `+0.05/h`，也不接受其他来源的心情恢复。
- 吽的 `+0.05/h` 作用于当前控制中枢所有干员；额外的 `+0.2/h` 只作用于同一控制中枢内的鲤氏侦探事务所干员，不跨站生效。
- 五人控制中枢中的令、夕、玛恩纳、薇薇安娜和焰尾：令与夕消耗 `0.75/h`，满心情可工作 32 小时；其余三人各获得夕、玛恩纳、薇薇安娜和焰尾分别提供的四份 `+0.05/h`，消耗 `0.55/h`，满心情可工作约 43.63636 小时。
- 心情已经为 0 的干员消耗率返回 0。

### 8.3 跨队列心情流转

- 以干员名为单位跨设施查找连续工作段，不要求固定在同一设施或同一槽位。
- 连续工作段首使用槽位显式设置的心情；未设置则为 24。
- 空位、换人、进入宿舍或心情设置为 0 都会中断工作段，下一次从 24 开始。
- 每经过一个队列，扣除该队列的 `消耗率 × 队列时长`，最低为 0。
- 循环排班时，如果干员同时在最后和第一个队列工作，第一个队列可继承最后一个队列结束后的心情；第一个队列显式设置的心情优先。
- 剩余心情：`max(0, 进驻心情 - 消耗率 × 队列时长)`。

### 8.4 曲线技能和工作时长

- 心情大于 0 的工作槽位按完整队列时长工作，心情消耗不会按比例截断效率。
- 技能的连续工作小时从前面连续队列累计；队首按循环规则从队尾继承。
- 心情为 0 的槽位工作时长为 0，技能不激活。
- `curve.ramp` 按小时计算档位，并按队列内各小时的时长加权平均。
- `workHours` 条件使用 `进入本队列前累计工作小时 + 当前队列时长` 判断。

## 9. 宿舍自动休整候选规则

宿舍恢复属于效率计算的一部分，但实现复杂度明显高于固定效率，建议作为第二个可独立测试的模块。

### 9.1 基础恢复速度

每个队列、每座宿舍独立计算：

`恢复速度 = 1.5 + 0.1 × 宿舍等级 + 0.0004 × 本宿舍氛围 + 技能恢复加成`

本宿舍氛围 = 宿舍等级 × 1000，不使用全基建宿舍总氛围。

### 9.2 自动休整分配

- 工作段结束后心情低于目标值、且下一队列不再工作时，干员进入自动休整候选。
- 目标心情是工作槽位显式设置的心情；未设置时为 24，显式 0 的目标为 0。
- 按队列 2 -> ... -> 最后队列 -> 队列 1 单次遍历，不循环收敛。
- 先按当前心情从低到高分配，同心情按当前队列进驻顺序；宿舍优先选择技能恢复速度高的空槽。
- 手动放在宿舍的干员占用槽位，不被自动休整覆盖。
- 自动休整者按精英 0、等级 0 激活宿舍技能；手动进驻者按自己的练度。
- 宿舍技能全员型按对应 `maxGroup` 取最高，单体型和均摊型使用独立规则；菲亚梅塔的阻断恢复和心情互换单独处理。

## 10. 技能 JSON 的基础消费规则

当前项目技能 JSON 已将技能描述转换为效果中间表示。基础计算器至少需要支持：

- `value`：固定数值。
- `per`：按设施等级、设施数量、干员数量、阵营数量、基地点数、订单上限或仓库容量等运行时计数换算。
- `condition`：设施进驻、基建进驻、阵营计数、心情、工作时长、线索交流等条件。
- `recipe`：制造站技能只对指定产品类型生效。
- `scope` / `facilities`：明确技能作用对象和跨设施范围。
- `stack: "max"` + `maxGroup`：同组候选先按来源干员合并，再按干员取最高；普通加成与最高值组相互独立。
- `moodCheck`：只在技能 JSON 标记时过滤心情 0 的被查询干员。
- `facBase`：设施基础效率层，不受 `zeroOpBonus` 清零。
- `storageCap` / `orderLimit`：先在属性层计算，再供容量和特殊技能读取，不直接进入效率百分比。
- `tradeOrder`：在贸易站订单概率/金额层处理，不与 `tradeSpd` 混合。
- `basePointGain` / `basePointConvert`：先计算基地点数；`basePointConvert` 保留来源点数，并按比例向目标点数追加派生值，再供其他 `per.source: "basePoint"` 效果读取。

当前生成结果的具体字段和设施 key 以当前项目 `干员技能JSON规范.md` 为准，不沿用旧项目的 `ctrl`、`trade`、`manu` 等设施 key。
